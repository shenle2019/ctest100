# 模块 05 · 编译调试工具链

> 内容整理自本仓库早期 README 的 gcc / Makefile / gdb 笔记，配合全部 100 题练习使用。C 程序从源码到可执行文件要过四道工序，工欲善其事必先利其器。

## 学习目标

学完本模块你应该能：

1. 说清预处理、编译、汇编、链接四步各自干了什么
2. 熟练使用 gcc 的常用参数（-o -c -g -Wall -O2 等）
3. 会写简单的 Makefile，理解依赖关系和三个自动变量
4. 用 gdb 打断点、单步、查看变量定位 bug

## 1. 从源码到可执行文件：四步走

以 `hello.c` 为例，一个 C 程序要经过四道工序：

| 步骤 | 产物 | gcc 参数 | 干了什么 |
|---|---|---|---|
| 预处理 | `hello.i` | `-E` | 展开 `#include`、`#define` 宏 |
| 编译 | `hello.s` | `-S` | 翻译成汇编代码 |
| 汇编 | `hello.o` | `-c` | 翻译成机器码（目标文件） |
| 链接 | `hello`（可执行） | 默认 | 把目标文件和库函数接起来 |

对应文件关系：

```
hello.c : 最初的源代码文件
hello.i : 经过编译预处理的源代码
hello.s : 汇编处理后的汇编代码
hello.o : 编译后的目标文件，机器码有了，但它引用的库函数地址还没填上
```

一条命令看全部中间产物：

```bash
gcc -Wall -c -save-temps hello.c   # 生成 hello.i、hello.s、hello.o
```

## 2. gcc 常用参数

### 编译选项

| 参数 | 含义 |
|---|---|
| （无） | `gcc hello.c` 直接编译链接，生成 `a.out`（Windows 是 a.exe） |
| `-o` | 指定输出文件名：`gcc -o hello hello.c` |
| `-c` | 只编译不链接，产生 `hello.o` 目标文件 |
| `-S` | 只生成汇编源文件 `hello.s` |
| `-E` | 只预处理，输出到标准输出，可重定向 `gcc -E hello.c > hello.txt` |

### 优化选项

| 参数 | 含义 |
|---|---|
| `-O` | 基本优化（Optimize） |
| `-O2` | 最大优化 |
| `-O0` | 不优化（默认，调试用） |

### 调试与警告

| 参数 | 含义 |
|---|---|
| `-g` | 编译时加入调试信息，供 gdb 使用。**不加 -g，gdb 里看到的全是内存地址**，没有函数名和变量名 |
| `-pg` | 加入剖析信息，供 gprof 做性能分析 |
| `-Wall` | 显示所有常用警告 |
| `-W` | 显示更多警告（变量未使用、逻辑错误等） |
| `-Werror` | 有警告就不编译。建议新手用，强迫自己把所有警告当错误修掉 |
| `-lm` | 链接数学库（`sqrt`、`pow` 等，Linux 上必须） |

常用组合：

```bash
gcc -g -Wall -o test001 test001.c    # 练习代码的标准编译姿势
gcc -O2 -o release hello.c           # 发布版：最大优化，不加重试信息
```

> 踩坑：改完代码忘了重新编译，跑的还是旧程序——「代码明明改了怎么结果不变」。编译型语言的日常：**改完必须重新编译**。另外，开着 `-Wall` 出现的警告每条都看，警告里常藏着真 bug。

## 3. Makefile：多文件编译

单文件用 gcc 直接敲。文件一多，每次重新敲一长串命令又慢又容易错，这就是 Makefile 要解决的问题。

### 为什么需要它

假设项目有两个源文件：

```c
/* main.c */
#include "mytool1.h"
int main(int argc, char **argv)
{
    mytool1_print("hello");
    return 0;
}

/* mytool1.h */
#ifndef _MYTOOL_1_H
#define _MYTOOL_1_H
void mytool1_print(char *print_str);
#endif

/* mytool1.c */
#include "mytool1.h"
#include <stdio.h>
void mytool1_print(char *print_str)
{
    printf("This is mytool1 print %s\n", print_str);
}
```

手工编译要三条命令：

```bash
gcc -c main.c
gcc -c mytool1.c
gcc -o main main.o mytool1.o
```

文件少还能忍，几百个源文件时全量重编是灾难。Makefile 记住**依赖关系**，只重编改动的部分。

### 基本写法

```makefile
# 注释用 # 开头
main: main.o mytool1.o
	gcc -o main main.o mytool1.o

main.o: main.c mytool1.h
	gcc -c main.c

mytool1.o: mytool1.c mytool1.h
	gcc -c mytool1.c
```

格式：

```
target: components
TAB rule
```

第一行描述依赖关系，第二行是规则（**必须以 TAB 开头**，不是空格）。语义：目标（target）依赖 components，当依赖比目标新（改过了），就执行规则重建目标。

改完 `mytool1.c` 敲一下 `make`，它只重编 `mytool1.o` 和 `main`，`main.o` 碰都不碰。

### 三个自动变量

| 变量 | 含义 |
|---|---|
| `$@` | 目标文件 |
| `$^` | 所有依赖文件 |
| `$<` | 第一个依赖文件 |

用它们简化上面的 Makefile：

```makefile
main: main.o mytool1.o
	gcc -o $@ $^

main.o: main.c mytool1.h
	gcc -c $<

mytool1.o: mytool1.c mytool1.h
	gcc -c $<
```

### 缺省规则

`.c.o` 表示所有 `.o` 都依赖对应的 `.c`，还能再简化：

```makefile
main: main.o mytool1.o
	gcc -o $@ $^

.c.o:
	gcc -c $<
```

> 踩坑：规则行必须用 TAB 缩进，编辑器把 TAB 转成空格后 `make` 报 `missing separator`。这是 Makefile 头号坑。

## 4. gdb：调试器

`printf` 大法能解决一半问题，剩下的一半交给 gdb。它主要帮你完成四件事：

1. 按你的要求启动程序、控制运行
2. 在指定断点停住（断点可以是条件表达式）
3. 停住时检查变量、内存、调用栈
4. 动态改变程序的执行流程

### 基本用法

```bash
gcc -g -Wall -o test001 test001.c   # 先带 -g 编译
gdb ./test001                       # 进入 gdb
```

### 常用命令

| 命令 | 缩写 | 作用 |
|---|---|---|
| `help` | `h` | 查看帮助，`help breakpoints` 分类查看 |
| `file 程序名` | | 载入要调试的可执行程序 |
| `run` | `r` | 运行程序，可带参数 `run arg1 arg2` |
| `break 行号/函数名` | `b` | 设断点：`break 10`、`break main`、`break test001.c:25` |
| `condition` | `cond` | 条件断点：`cond 1 x > 100`（断点 1 在 x>100 时才停） |
| `next` | `n` | 单步执行，**不进入**函数内部 |
| `step` | `s` | 单步执行，**进入**函数内部 |
| `continue` | `c` | 继续运行到下一个断点 |
| `until` | `u` | 跳出循环体（厌倦跟踪 for 循环时用） |
| `print 变量` | `p` | 打印变量值：`print x`、`print arr[3]` |
| `display 变量` | | 每次停下自动显示该变量 |
| `info breakpoints` | `i b` | 查看断点信息 |
| `info locals` | | 查看当前函数所有局部变量 |
| `backtrace` | `bt` | 查看调用栈（崩溃后找调用链最有用） |
| `list` | `l` | 显示源码 |
| `quit` | `q` | 退出 |

### 典型排障流程

```bash
gdb ./test001
(gdb) break 15          # 在可疑行打断点
(gdb) run               # 跑到断点停住
(gdb) print x           # 检查变量是不是预期值
(gdb) next              # 一步步走，看哪一步值变错
(gdb) quit
```

段错误（Segmentation fault）排查：程序崩溃后 gdb 里敲 `bt`（backtrace），调用栈最上面就是崩的位置。

> 踩坑：gdb 里看到的全是地址，八成是编译时忘了 `-g`。调试完发布时再用 `-O2` 重新编译，调试版和执行版别混用。

## 5. 工具链速查总结

| 需求 | 命令 |
|---|---|
| 编译一个文件 | `gcc -Wall -o a a.c` |
| 看预处理结果 | `gcc -E a.c > a.i` |
| 只编译成目标文件 | `gcc -c a.c` |
| 调试编译 | `gcc -g -Wall -o a a.c` |
| 多文件增量编译 | `make`（配 Makefile） |
| 交互式调试 | `gdb ./a` |
| 性能分析 | `gcc -pg` + `gprof ./a.out` |
